All three projects are **created at runtime** by `run_onboarding_tests.py`
through the same wizard endpoints (`/api/resource/<DocType>` + the
`activate_project` RPC) the browser wizard uses. **Nothing is pre-seeded

### 0.1 RW-WB — Rwanda 6-level (World Bank canonical)

```
Country → Province → District → Sector → Cell → Village
```

Justification: long hierarchy, the canonical reference layout.

### 0.2 KE-EAC — Kenya 5-level (devolution-era)

```
Country → County → Sub-County → Ward → Village
```

Justification: same depth class but **different label set** —
catches any hardcoded `"District"`/`"Province"` assumptions.

### 0.3 STJ-HOSP — St. John Hospital 4-level (non-geographic)

```
Hospital → Department → Unit → Ward
```

Justification: **organisational** tiers, not geographic regions —
catches any code path that assumes "admin level == administrative
region in a country."

> All three projects coexist on the same site. Cross-project IDOR is
> a primary security target (see §6).

## 2. Onboarding tests (`run_onboarding_tests.py`)

Drives the actual wizard end-to-end, asserting that each REST insert
succeeds and the final `activate_project` RPC flips `is_active=1`.
The suite emits `wizard_state.json` with the named records every
downstream suite consumes.

| ID | Step | Endpoint | Expected |
|----|------|----------|----------|
| OB-{code}.step1_create_project | wizard step 1 | `POST /api/resource/GRM Project` | 200/201, `data.name == project_code` (autoname=`field:project_code`) |
| OB-{code}.level.{n}_created | wizard step 5 | `POST /api/resource/GRM Administrative Level Type` | 200/201 (autoname=`hash`) |
| OB-{code}.region.{n}_created | wizard step 6 | `POST /api/resource/GRM Administrative Region` | 200/201, parented (autoname=`hash`) |
| OB-{code}.dept.{n} | wizard step 8 | `POST /api/resource/GRM Issue Department` with `grm_project_link: [{project: <name>}]` | 200/201 |
| OB-{code}.cat.{n} | wizard step 7 | `POST /api/resource/GRM Issue Category` with `label`, `abbreviation`, `assigned_department`, `confidentiality_level`, `redirection_protocol`, `grm_project_link` | 200/201 |
| OB-{code}.type.{n} / status.{n} / age.{n} / citizen_group.{type}.{name} | wizard steps 7/10/11 | matching catalog endpoints with `grm_project_link` child Table | 200/201 |
| OB-{code}.step4_create_project_role | wizard step 4 | `POST /api/resource/GRM Project Role` w/ `is_active=1` and 6 default `duties` rows | 200/201 (REQUIRED — `activate_project` rejects projects with no active role) |
| OB-{code}.step12_activate | wizard step 12 | `egrm.egrm.page.grm_project_wizard.grm_project_wizard.activate_project` | 200, message dict-or-str |
| OB-{code}.is_active=1 / is_setup_complete=1 | verification | `GET /api/resource/GRM Project/<name>` | both flags == 1 |

Important payload-shape facts (cross-checked against the DocType JSONs):

* All catalog DocTypes (Category/Type/Status/Department/AgeGroup/CitizenGroup)
  link to their project via the `grm_project_link` child Table, NOT a
  direct `project` field. Sending `"project": <name>` is silently ignored.
* `GRM Issue Citizen Group.group_type` is a Select with options `"1"|"2"`
  (per the wizard form default).
* `GRM Project.is_active` and `current_setup_step` are server-managed:
  the wizard does NOT send them on insert; `activate_project` flips them
  to `(1, 12)` after gating on the project-role + admin-level-type checks.
* The 6 canonical duties (`Intake`, `Review`, `Assignment`,
  `Investigate & Resolve`, `Feedback`, `Supervise`) are seeded by patch
  `egrm.patches.v16_0.seed_duty_catalog` and are referenced by `name`.

Run with `ACTOR_PROJECT_ADMIN` (only platform-admin role can call
`activate_project`).

## 11. Performance tests (`run_performance_tests.py`)

Per-endpoint budgets are the **single source of truth** in
`_common.py::PERF_BUDGETS`. Every PF-* assertion below feeds through
`check_budget(suite, label, key, value, field)` so the dev gets one
canonical number to chase, not a number scattered across docs and
code. The whole point of these budgets is to **force the developer
to use caching, `frappe.qb`, raw SQL, and bulk-insert fast paths** —
the `<100 ms` location-cascade target in particular cannot be hit by
row-at-a-time ORM access.

## 14. How to run

### Step 0 — Clean DB + browser deps (REQUIRED before the first run)

The suite assumes a clean database. Always start from reinstall:

```bash
# from /Users/victor/egrm/apps/egrm
bench --site egrm.local --force reinstall

# Re-provision the test users (idempotent helper that creates the 9
# @egrm.test accounts the suite expects).
bench --site egrm.local execute egrm.cli.sync_test_users.sync

# One-time browser install for the UI-SCREENSHOTS sub-suite.
pip install playwright && playwright install chromium
```

> **Without** the reinstall step, leftover data from prior runs will
> cause project-code collisions (`RW-WB` already exists), assignment
> caches, and idempotency assertions to misbehave.

### Step 1 — Run the full suite

```bash
python /Users/victor/egrm/apps/egrm/docs/superpowers/plans/aqe-generated/run_full_suite.py
```

This runs every sub-suite in dependency order and writes per-suite JSON
plus an aggregate `REPORT.json` to
`/Users/victor/egrm/aqe-screenshots/aqe-full-suite/`.

### Step 2 — Run a single sub-suite

```bash
python .../aqe-generated/run_full_suite.py SECURITY
# or invoke directly
python .../aqe-generated/run_security_tests.py
```

Each sub-suite ends with one of:
- `[<NAME>] PASSED — N/N in <s>s` (exit 0)
- `[<NAME>] FAILED — K/N (failures: …) in <s>s` (exit 1)

> **Order matters.** ONBOARDING must run first; everything else reads
> `wizard_state.json` to find the records ONBOARDING produced.
